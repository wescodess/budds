# Phase C1 storage contract

Storage version: `learn-v2.measurement-storage.v1`. Implements the storage and enumeration slice of [C1.1](https://github.com/wescodess/budds/issues/421) in [Spec C1](https://github.com/wescodess/budds/issues/413), together with the serial shared and disabled public contracts. Report runs and cells pin the revised output `learn-v2.measurement-report.v3`; report source is v3; query and metric definitions remain v1. This document does not freeze a baseline protocol or complete the spec.

The accepted resolutions on [responses](https://github.com/wescodess/budds/issues/363#issuecomment-6651831618), [items/exposure](https://github.com/wescodess/budds/issues/364#issuecomment-6651739355), [reports](https://github.com/wescodess/budds/issues/366#issuecomment-6652156993), [disclosure](https://github.com/wescodess/budds/issues/373#issuecomment-6651824980) and [scorer identity](https://github.com/wescodess/budds/issues/380#issuecomment-6651838342) govern this contract. The original orchestrator brief is unchanged.

## Ownership and pins

All 24 collections require `userId`, `storageVersion`, `createdAt`, and `by_userId`. All reads and cleanup use pages/batches of at most eight. The registry is `shared/learn-v2-measurement-storage-manifest.ts`; storage validators live only under `convex/lib/learnV2MeasurementStorage.ts`, with tables/indexes in `convex/schema.ts`.

V2 scope requires the Void, Blueprint revision, objective, Blueprint record revision, assessment-contract version/digest and depth. Context is discriminated: calibration, a planned measurement with complete plan pins, or a session with complete plan/session/content/generator pins and optional complete Canvas attribution. Standalone diagnostics require their owned thread/activity and revisions, with no invented V2 anchors. Child rows repeat their aggregate anchor for indexed cleanup.

Measurement item pins require the item/revision/prompt digest, stable case, family/revision/form/equivalence, novelty policy, private scoring-spec revision/digest, support manifest and publication validation. Published available items and available scoring specs require their payloads; purged revisions preserve identity with unavailable evidence. Candidate/quarantined inventory may be assembled before its validation/spec exists. Ordinary application and calibration opportunities use their existing content/assessment authority and do not acquire a measurement-family identity.

Admission is absent in this slice. Every new storage capability is false. Admitted assignment shapes require frozen protocol, allocation, scorer and scheduling pins; considered/unmeasurable rows can remain `protocol_not_frozen`. A full allocation has three distinct case slots for cold/day 7/day 30; a two-case allocation declares one delayed horizon. Consistency, numeric/byte limits, semantic uniqueness and command validation are enforced by the following serial contracts before any writer can be enabled.

## Collection policy matrix

`M` means an explicit metadata allowlist in both direct Convex and HTTP ZIP export; it withholds prompts, keys, rubrics, solutions, private evidence, seeds, fingerprints and scorer payloads. `R` exports the owned canonical answer once after checking its submission, aggregate and current evidence. `W` enumerates a bounded page but exports no grant rows. Every row is removed by account deletion; report runs additionally drain their indexed children across the source-owner roster.

Indexes below omit the common `userId` prefix. Dotted fields use underscores in index names. The registry lists every exact field order.

## Report cell v3

`reportCellFields` embeds the complete `learnReportMetricValidator.fields` alongside `reportVersion`, `reportRunId`, `cellKey`, `sequence` and the existing owner/storage fields. Public cell pages and aggregate exports reuse that same validator. A stored cell therefore preserves every frozen output field, including `weighting`, typed `stratum`/`status`, estimates and breakdowns. The previous single `count`/`value`/bounds and free-text stratum/status are replaced. This is an inactive pre-admission contract change with no enabled cell writer or migration.

All numeric counts are integers from 0 through 10,000. The shared parser enforces finite values, nested populations, disjoint disposition totals and estimate null/reason rules before a future writer persists a cell; public pages additionally retain the eight-cell/256 KiB ceiling. Convex return validators enforce the identical closed shape. The query version and `verified_learning_gain.v1` / `false_mastery_next_delayed.v1` arithmetic are unchanged.

[#511](https://github.com/wescodess/budds/issues/511) advances report output to v3 and report source to v2. Query, storage and metric versions stay v1. The new required `legacyIndependentAudit` object has `unknownCount` (integer 0–10,000 or null) and its own `sourceCoverage` (`complete` or `unknown`). Complete enumeration requires a numeric count, including a measured zero; unknown enumeration requires null. This separates unverifiable provenance in enumerated legacy Independent history from an unknown inventory size. Old report-output v1/v2 and source v1 envelopes are rejected. These inactive shapes require no migration.

The source v3 `owner_watermark` snapshot requires the same `legacyIndependentAudit` object, using the single cell validator's field in storage. Its count is the source owner's legacy Independent capabilities at the frozen epoch start whose Independent provenance cannot be verified, read from permitted history through the snapshot's saved source watermark. The adapter must explicitly supply unknown/null when it cannot enumerate that history; absence is never defaulted to zero. The shared snapshot schema requires `historyCoverage = unknown` to carry `legacyIndependentAudit.sourceCoverage = unknown` and a null count. Complete history permits either a complete audit with a count or an unknown audit with a null count; history coverage alone does not establish audit enumeration. One owner audit is included per roster owner per run. Aggregate cells repeat the cohort/epoch total independently of horizon, weighting and prospective strata; the shared page schema requires identical audit coverage and count in every cell on a page. Consumers display it once, never sum it across cells. It never contributes to prospective episodes, gate claims, paired outcomes, attrition, rates or missing-outcome bounds. The later source adapter owns enumeration and deduplication; no reader or writer is added here.

## 517 report source v3

[#517](https://github.com/wescodess/budds/issues/517) advances only the source to `learn-v2.measurement-report-source.v3`. Source v1/v2 envelopes are rejected by the inactive facts, watermarks and report rows; no migration is needed. Report output remains v3, and query, storage and metric versions remain v1. `learnV2MeasurementReportContract.ts` supplies the single structural validators reused by report facts and row snapshots, with exact shared/storage type regressions. The shared schemas enforce the semantic refinements before persistence or computation; Convex validators alone cannot enforce cross-field equality.

| Binding decision | Frozen source fields and consistency |
| --- | --- |
| 1. Computation identities | Episodes and first-check claims require `learnerKey` and `capabilityKey`. Owner-wide watermarks require only `learnerKey`; they have no `capabilityKey`. The owner clarified #517: #366 specifies a per-owner source-watermark vector and an owner-wide legacy audit, so capability identity applies only to episode and first-check claim rows. Episodes additionally require `assignmentId`, `learningVoidId`, `blueprintRevisionId`, `objectiveId` and `horizonDays`, plus cold/original/replacement opportunity IDs and each accepted submission/result identity. `horizonDays` remains known without an anchor/clock and must match any clock. |

| 4. Linked replacements | `replacementOpportunityId`, `replacementAcceptance` and `replacement` retain a distinct delayed slot using the original acceptance/result schemas. A replacement requires a distinct original opportunity; unlinked acceptance/results, reused endpoint submissions/attempts and incorrect endpoint kinds fail. `replacementPolicy` reuses the output policy schema: explicit `secondary_only`, or `predeclared` with `protocolVersion`, `ruleVersion`, `ruleDigest`. A frozen assignment requires a policy; its predeclared protocol must equal the assignment's. The policy is copied from the protocol frozen before enrollment, never inferred from replacement success. Key derivation is fixed by `deriveLearnReportLearnerKey` / `deriveLearnReportComputationKeys`. Let `H(parts)` be `sha256:` plus the lowercase SHA-256 hex of UTF-8 `JSON.stringify(parts)`. The learner key is `H(["learn-v2.measurement-report-keys.v1", "learner", reportRunId, ownerTokenIdentifier])`. The settled capability scope is exactly `H(["learn-v2-mastery-scope.v1", ownerTokenIdentifier, blueprintRevisionId, objectiveId])`; the capability key is `H(["learn-v2.measurement-report-keys.v1", "capability", reportRunId, scopeKey])`. The full authenticated `tokenIdentifier` is used, including issuer. Void and assignment distinguish the episode, not the settled capability. Changing the run changes both keys; changing capability preserves the learner key. Writers must derive keys from the pinned roster and canonical scope on every row, never accept supplied aliases or random per-row keys. The raw identity and scope digest are not added to snapshots.

The run reconciles its complete pinned roster of derived learner keys against exactly one owner-wide watermark per owner, including owners with no episodes or claims. `reconcileLearnReportSourceRows` checks the combined validated rows across all pages: a missing watermark, duplicate roster owner, owner outside the roster, exact duplicate or conflicting row is `incomplete`, with payload-free reason codes. Episode uniqueness is assignment + horizon; it retains the full owner/Void/Blueprint/objective/assignment tuple and opportunity/submission/attempt pins for joins. Claims are unique per learner + capability + epoch, so a later claim or retry cannot replace the first. Cross-horizon assignment/cold snapshots and capability-key bindings must agree. Pagination, saved watermarks, roster/key derivation and complete source enumeration remain adapter obligations; a page alone cannot establish completeness. Retries must reuse the saved page, not append another copy.

Reconciliation also enforces these outcome and claim identities across the entire run, independently of the supplied capability key:

- Each original delayed opportunity, replacement opportunity, and submission, attempt or execution used by either endpoint belongs to exactly one assignment/horizon episode. The same delayed outcome cannot serve both day 7 and day 30, or another assignment. Cold opportunity, acceptance and result identities belong to one assignment; identical cold snapshots may repeat across that assignment's horizon rows. Reuse outside these scopes yields `reused_outcome_identity`.
- Every occurrence of an opportunity, submission, attempt or execution must agree on its opportunity identity and byte-identical acceptance/result snapshots, including null versus present snapshots. Contradiction yields `conflicting_outcome_snapshot`. If a first-check claim shares any of these identities with an episode, its `learnerKey` and `capabilityKey` must equal that episode's, and the shared slot must be its original delayed or replacement slot, never its cold slot. Breaches yield `claim_learner_mismatch`, `claim_capability_mismatch` or `claim_shared_cold_slot`, respectively, even for unscored outcomes. Identical snapshots alone do not establish #366's owner, capability and qualifying delayed-slot predicates. Sharing a replacement outcome does not replace a claim's fixed first-check slot or change the frozen replacement policy.
- A claim sharing an episode's original delayed slot must also agree on the opportunity's frozen window: `protocolVersion`, `schedulingPolicyVersion`, `horizonDays`, `timezone`, `dueLocalDate`, `dueAt`, `openAt` and `closeAt`. A mismatch or absent episode clock yields `conflicting_slot_window`, including unanswered and unscored slots. [#366 §§2–3](https://github.com/wescodess/budds/issues/366#issuecomment-6652156993) fixes the first next scheduled qualifying slot before its outcome and matures an opportunity at `closeAt <= cutoff`; conflicting windows cannot establish one denominator. The clock's `anchorKind`, `anchorEventId` and `anchorAt` instead describe the episode's protocol anchor or the claim's Independent attainment and may legitimately differ; they are excluded from this comparison. The episode carries only its original clock, so a claim sharing a replacement has no replacement window to compare: window consistency for that case remains unverified by source v3, covered only by the identical acceptance/result snapshot rule above. Never compare a replacement's window with the original's.
- Source rows are grouped by identity before diagnostics: repeated byte-identical snapshots yield `duplicate_source_row`, distinct snapshots yield `conflicting_source_row`, and both reasons apply when a group has both. The reason set is independent of row order.
- Each `claim.claimKey` occurs once, each basis attempt yields at most one first claim, and each first-check opportunity serves at most one claim, regardless of learner, capability key or epoch. These checks apply alongside learner/capability/epoch uniqueness and yield `duplicate_claim_key`, `reused_claim_basis_attempt` or `reused_first_check_opportunity`, respectively.

Every breach makes reconciliation `incomplete`, with specific, sorted, payload-free reason codes; no row is silently dropped or selected over another. These are narrowing rules within source v3, with no additional version change.

An incomplete reconciliation cannot seal a complete report: source/population coverage remains unknown or the run fails, never silently drops rows. A missing or unknown owner legacy audit makes the cohort legacy audit unknown/null; the cohort audit must also agree across every page. These are run-level obligations for C6.1/C6.2, beyond the existing per-cell-page audit equality refine.

Keys are computation inputs only. Closed report cells, public pages, safe manifests and aggregate exports contain neither key. Direct owner and HTTP ZIP exports continue to withhold entire source snapshots; their existing explicit metadata allowlists are unchanged. Reconciliation diagnostics contain only status/reason codes, and derivation/validation emit no logs. Regressions inject both keys into public/aggregate returns, inspect both actual owner export paths, and assert no computation keys in outputs or logs. No writer, migration, flag or provider operation is added.

## Compatibility and cleanup boundaries

### #512 response pins

[#512](https://github.com/wescodess/budds/issues/512) applies [#363 §§1–3](https://github.com/wescodess/budds/issues/363#issuecomment-6651831618) without a writer, migration or flag. Existing `learn-v2.responses.v1` commands, stored legacy assessment responses (`flow = v2_today | v2_canvas` with their historical `baselineEpoch`) and formative/diagnostic branches retain their shapes and meaning. New assessment response storage uses `responseContextVersion = learn-v2.response-context.v1`, `flow = today | canvas`, and a required `measurementContext`: either `{ status: not_enrolled }` with no epoch, or `{ status: admitted, assignmentId, baselineEpoch }`. Only an admitted assignment supplies that epoch; considered/not-admitted assignments never fabricate one.

The frozen pure function `shared/learn-v2-measurement.ts::deriveLearnAssessmentResponseContext` consumes projected, server-read opportunity context and assignment pins. It has no client-authority input or I/O. The parent's clarified rules are:

| Context | Server authority for response flow | Fail-closed cases |
| --- | --- | --- |
| `session` | Session without Canvas attribution is Today; complete Canvas attribution is Canvas. | Malformed session/Canvas pins or a conflicting admitted assignment flow. |
| `planned_measurement` | Admitted measurement assignment's frozen `v2_today` / `v2_canvas` flow, mapped to `today` / `canvas`. | Missing, considered or not-admitted assignment, missing epoch/identity, or unknown flow. New stored planned responses also require admitted measurement context. |
| `calibration` | Explicit `contextPins.origin = today | canvas`, set by the future server creator: V2 calibration route is Today; Adaptive Canvas is Canvas. | Missing/unknown origin or a conflicting admitted assignment flow. Calibration is never defaulted to Today. |

Calibration `origin` is optional only in legacy opportunity/scope shapes so old rows still read; the derivation and new accepted-response storage require it. This clarification is prospective and supplies no calibration writer or backfill. Request schemas reject client `flow`, epoch, measurement context, origin and confidence policy.

`learn-v2.response-delivery-pins.v1` pins `confidenceRequested: boolean` on an opportunity's optional `deliveryPins`; response slots store `confidenceRequested` directly. Future creators/granters must set these from the actual delivered prompt contract, including explicit false. Legacy missing pins resolve to false; the shared slot parser materializes that false. `validateLearnAcceptResponseRequest` compares single-response confidence against the owned slot or validated assessment delivery pins. `validateLearnFinalResponseBundle` independently checks teach-back against its slot's `confidenceRequested` and application against its opportunity's `deliveryPins`, using `resolveLearnResponseConfidenceRequested` for each. `validateLearnMasterySubmission` in the public contract dispatches the strict `{ submission: command }` envelope to the single or bundle validator. Both shapes require integer 1–5 confidence exactly when the relevant server pin requests it, rejecting missing requested confidence and unsolicited confidence without adding a learner interaction. C2.1 must call these helpers with the owned server-read pins before persistence.

Receipts add `result.kind = terminalized` under `commandVersion = learn-v2.response-terminalization.v1`. The result retains the exact `target`, resulting `revision`, `reasonCode = cancelled | abandoned`, and server `terminalizedAt`. The terminalized branch requires the target and forbids `expiresAt`; it follows owning aggregate/account history and the existing command-key index, so C2.1 can replay that same result. A browser close creates no receipt or abandonment fact. Rejections still require their 90-day expiry. The disabled public terminalization success shape reserves `terminalizedAt` alongside its existing target/revision/reason.
