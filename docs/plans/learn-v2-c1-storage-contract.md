# Phase C1 storage contract

Storage version: `learn-v2.measurement-storage.v1`. Implements the storage and enumeration slice of [C1.1](https://github.com/wescodess/budds/issues/421) in [Spec C1](https://github.com/wescodess/budds/issues/413), together with the serial shared and disabled public contracts. Report runs and cells pin the revised output `learn-v2.measurement-report.v3`; report source is v3; query and metric definitions remain v1. This document does not freeze a baseline protocol or complete the spec.

The accepted resolutions on [responses](https://github.com/wescodess/budds/issues/363#issuecomment-6651831618), [items/exposure](https://github.com/wescodess/budds/issues/364#issuecomment-6651739355), [reports](https://github.com/wescodess/budds/issues/366#issuecomment-6652156993), [disclosure](https://github.com/wescodess/budds/issues/373#issuecomment-6651824980) and [scorer identity](https://github.com/wescodess/budds/issues/380#issuecomment-6651838342) govern this contract. The original orchestrator brief is unchanged.

## Ownership and pins

All 29 collections require `userId`, `storageVersion`, `createdAt`, and `by_userId`. Enumeration and cleanup use pages/batches of at most eight. The registry is `shared/learn-v2-measurement-storage-manifest.ts`; storage validators live under `convex/lib/learnV2MeasurementStorage.ts` and `convex/lib/learnV2ArtifactLineageContract.ts`, with tables/indexes in `convex/schema.ts`. The #516 lookup has its separate finite graph bounds below.

V2 scope requires the Void, Blueprint revision, objective, Blueprint record revision, assessment-contract version/digest and depth. Context is discriminated: calibration, a planned measurement with complete plan pins, or a session with complete plan/session/content/generator pins and optional complete Canvas attribution. Standalone diagnostics require their owned thread/activity and revisions, with no invented V2 anchors. Child rows repeat their aggregate anchor for indexed cleanup.

Measurement item pins require the item/revision/prompt digest, stable case, family/revision/form/equivalence, novelty policy, private scoring-spec revision/digest, support manifest and publication validation. Published available items and available scoring specs require their payloads; purged revisions preserve identity with unavailable evidence. Candidate/quarantined inventory may be assembled before its validation/spec exists. Ordinary application and calibration opportunities use their existing content/assessment authority and do not acquire a measurement-family identity.

Admission is absent in this slice. Every new storage capability is false. Admitted assignment shapes require frozen protocol, allocation, scorer and scheduling pins; considered/unmeasurable rows can remain `protocol_not_frozen`. A full allocation has three distinct case slots for cold/day 7/day 30; a two-case allocation declares one delayed horizon. Consistency, numeric/byte limits, semantic uniqueness and command validation are enforced by the following serial contracts before any writer can be enabled.

## Collection policy matrix

`M` means an explicit metadata allowlist in both direct Convex and HTTP ZIP export; it withholds prompts, keys, rubrics, solutions, private evidence, seeds, fingerprints and scorer payloads. `R` exports the owned canonical answer once after checking its submission, aggregate and current evidence. `W` enumerates a bounded page but exports no grant rows. Every row is removed by account deletion; report runs additionally drain their indexed children across the source-owner roster.

## Report cell v3

`reportCellFields` embeds the complete `learnReportMetricValidator.fields` alongside `reportVersion`, `reportRunId`, `cellKey`, `sequence` and the existing owner/storage fields. Public cell pages and aggregate exports reuse that same validator. A stored cell therefore preserves every frozen output field, including `weighting`, typed `stratum`/`status`, estimates and breakdowns. The previous single `count`/`value`/bounds and free-text stratum/status are replaced. This is an inactive pre-admission contract change with no enabled cell writer or migration.

All numeric counts are integers from 0 through 10,000. The shared parser enforces finite values, nested populations, disjoint disposition totals and estimate null/reason rules before a future writer persists a cell; public pages additionally retain the eight-cell/256 KiB ceiling. Convex return validators enforce the identical closed shape. The query version and `verified_learning_gain.v1` / `false_mastery_next_delayed.v1` arithmetic are unchanged.

[#511](https://github.com/wescodess/budds/issues/511) advances report output to v3 and report source to v2. Query, storage and metric versions stay v1. The new required `legacyIndependentAudit` object has `unknownCount` (integer 0–10,000 or null) and its own `sourceCoverage` (`complete` or `unknown`). Complete enumeration requires a numeric count, including a measured zero; unknown enumeration requires null. This separates unverifiable provenance in enumerated legacy Independent history from an unknown inventory size. Old report-output v1/v2 and source v1 envelopes are rejected. These inactive shapes require no migration.

The source v3 `owner_watermark` snapshot requires the same `legacyIndependentAudit` object, using the single cell validator's field in storage. Its count is the source owner's legacy Independent capabilities at the frozen epoch start whose Independent provenance cannot be verified, read from permitted history through the snapshot's saved source watermark. The adapter must explicitly supply unknown/null when it cannot enumerate that history; absence is never defaulted to zero. The shared snapshot schema requires `historyCoverage = unknown` to carry `legacyIndependentAudit.sourceCoverage = unknown` and a null count. Complete history permits either a complete audit with a count or an unknown audit with a null count; history coverage alone does not establish audit enumeration. One owner audit is included per roster owner per run. Aggregate cells repeat the cohort/epoch total independently of horizon, weighting and prospective strata; the shared page schema requires identical audit coverage and count in every cell on a page. Consumers display it once, never sum it across cells. It never contributes to prospective episodes, gate claims, paired outcomes, attrition, rates or missing-outcome bounds. The later source adapter owns enumeration and deduplication; no reader or writer is added here.

C6.1 must count `considered` candidates and `notAdmitted` assignments per **distinct `assignmentId`**, never per row or horizon. The candidate inventory includes every assignment status; the explicit status pins retain the considered versus not-admitted distinction, and distinguish `not_admitted` from `protocol_not_frozen` without a protocol-version proxy. E_h includes only admitted assignments with that horizon assigned and a matured original window.

Storage enumerates a non-admitted candidate once as an assignment, with no allocation. Its source representation is therefore one inventory row with canonical `horizonDays: 7`, both assignment flags false, and no clocks, opportunity IDs, acceptances or results. Here 7 is only an envelope placeholder; it creates neither a day-7 assignment nor a day-7 denominator and must not stratify admission counts by horizon. A second horizon row is rejected. The `(assignmentId, horizonDays)` identity diagnoses a repeated inventory row as `duplicate_source_row`; all occurrences of one assignment must retain the identical full assignment snapshot. Differing admission pins produce the existing `conflicting_assignment_snapshot` (and `conflicting_source_row` for the same row identity). Considered and blocked not-admitted candidates each reconcile as complete when their inventory and watermark are complete.

Key derivation is fixed by `deriveLearnReportLearnerKey` / `deriveLearnReportComputationKeys`. Let `H(parts)` be `sha256:` plus the lowercase SHA-256 hex of UTF-8 `JSON.stringify(parts)`. The learner key is `H(["learn-v2.measurement-report-keys.v1", "learner", reportRunId, ownerTokenIdentifier])`. The settled capability scope is exactly `H(["learn-v2-mastery-scope.v1", ownerTokenIdentifier, blueprintRevisionId, objectiveId])`; the capability key is `H(["learn-v2.measurement-report-keys.v1", "capability", reportRunId, scopeKey])`. The full authenticated `tokenIdentifier` is used, including issuer. Void and assignment distinguish the episode, not the settled capability. Changing the run changes both keys; changing capability preserves the learner key. Writers must derive keys from the pinned roster and canonical scope on every row, never accept supplied aliases or random per-row keys. The raw identity and scope digest are not added to snapshots.

The run reconciles its complete pinned roster of derived learner keys against exactly one owner-wide watermark per owner, including owners with no episodes or claims. `reconcileLearnReportSourceRows` checks the combined validated rows across all pages: a missing watermark, duplicate roster owner, owner outside the roster, exact duplicate or conflicting row is `incomplete`, with payload-free reason codes. Episode uniqueness is assignment + horizon; it retains the full owner/Void/Blueprint/objective/assignment tuple and opportunity/submission/attempt pins for joins. Claims are unique per learner + capability + epoch, so a later claim or retry cannot replace the first. All per-assignment snapshots, including admission/protocol status, and cross-horizon cold snapshots and capability-key bindings must agree. Pagination, saved watermarks, roster/key derivation and complete source enumeration remain adapter obligations; a page alone cannot establish completeness. Retries must reuse the saved page, not append another copy.

Reconciliation also enforces these outcome and claim identities across the entire run, independently of the supplied capability key:

- Each original delayed opportunity, replacement opportunity, and submission, attempt or execution used by either endpoint belongs to exactly one assignment/horizon episode. The same delayed outcome cannot serve both day 7 and day 30, or another assignment. Cold opportunity, acceptance and result identities belong to one assignment; identical cold snapshots may repeat across that assignment's horizon rows. Reuse outside these scopes yields `reused_outcome_identity`.
- Every occurrence of an opportunity, submission, attempt or execution must agree on its opportunity identity and byte-identical acceptance/result snapshots, including null versus present snapshots. Contradiction yields `conflicting_outcome_snapshot`. If a first-check claim shares any of these identities with an episode, its `learnerKey` and `capabilityKey` must equal that episode's, and the shared slot must be its original delayed or replacement slot, never its cold slot. Breaches yield `claim_learner_mismatch`, `claim_capability_mismatch` or `claim_shared_cold_slot`, respectively, even for unscored outcomes. Identical snapshots alone do not establish #366's owner, capability and qualifying delayed-slot predicates. Sharing a replacement outcome does not replace a claim's fixed first-check slot or change the frozen replacement policy.
- A claim sharing an episode's original delayed or replacement slot must also agree on that opportunity's frozen window: `protocolVersion`, `schedulingPolicyVersion`, `horizonDays`, `timezone`, `dueLocalDate`, `dueAt`, `openAt` and `closeAt`. Compare the original slot to `clock` and the replacement slot to `replacementClock`. A mismatch or absent original clock yields `conflicting_slot_window`, including unanswered and unscored slots; a linked replacement without its clock is rejected by the schema. [#366 §§2–3](https://github.com/wescodess/budds/issues/366#issuecomment-6652156993) fixes the first next scheduled qualifying slot before its outcome and matures each opportunity at its own `closeAt <= cutoff`; conflicting windows cannot establish one denominator. The clock's `anchorKind`, `anchorEventId` and `anchorAt` instead describe the episode's protocol anchor or the claim's Independent attainment and may legitimately differ; they are excluded from this comparison. Never compare a replacement's window with the original's.
- Source rows are grouped by identity before diagnostics: repeated byte-identical snapshots yield `duplicate_source_row`, distinct snapshots yield `conflicting_source_row`, and both reasons apply when a group has both. The reason set is independent of row order.
- Each `claim.claimKey` occurs once, each basis attempt yields at most one first claim, and each first-check opportunity serves at most one claim, regardless of learner, capability key or epoch. These checks apply alongside learner/capability/epoch uniqueness and yield `duplicate_claim_key`, `reused_claim_basis_attempt` or `reused_first_check_opportunity`, respectively.

### Identity pair audit (Stage A5)

The identity inventory is exhaustive for source-row joins. A claim carries `learnerKey`, `capabilityKey`, the learner/capability/epoch claim tuple, `claim.claimKey`, `claim.basisAttemptId`, `firstCheckOpportunityId`, `acceptance.submissionId`, and `result.submissionId` / `attemptId` / `executionId`. An episode carries the same computation keys, `assignmentId`, its owner/Void/Blueprint/objective scope, the assignment/horizon episode tuple, three opportunity IDs and three acceptance/result identity sets. A watermark carries only its owner `learnerKey`; `sequence` is an owner-local source revision, not another owner or outcome identity. Claim/check/fact/mastery revisions are likewise authority-local pins, not global join keys.

| Identity and fields | Every row pair where it can recur | Enforced consistency |

The result snapshot contract denotes an authoritative committed result; source reconciliation cannot authenticate that assertion from scalar rows. Writers must join the canonical submission → authoritative attempt → execution receipt, verify the pinned transition contract and mastery revision, and freeze the first qualifying attainment and its next slot transactionally. Writers must validate an absent basis as an authoritative valid unassisted `independent_application` pass that actually established Independent, with canonical acceptance/attainment time and pinned mastery revision. A visible measurement or retained-check basis always fails reconciliation; forged Independent scalars do not supply transition authority. If a basis attempt is absent from **all** result rows, as is legitimate for ordinary V2 attempts, its validity and attainment time remain entirely a writer obligation. Absence is not an invented failure or proof of validity. Key derivation, complete roster/page/fact enumeration, saved watermark sequences and authority-local revisions remain writer/adapter obligations too.

The Stage A5 regressions change only one learner or capability key at a time for both original and replacement slots in unanswered, unscored and scored states. Exact conflict-only diagnostics for `[A,B]` and `[B,A]` contain `conflicting_source_row` without `duplicate_source_row`; groups with an actual repeat retain both reasons. Basis regressions reject all four visible result endpoints, retained-transfer results and forged Independent transitions, self-reference and multiple contradictory occurrences; an absent ordinary V2 basis remains a writer obligation. Admission regressions distinguish complete considered and blocked not-admitted assignments, enforce frozen pins and allocated horizons, and reject duplicate/conflicting inventory rows.

At the documented maximum of 10,000 episodes and 64 MiB of source input, full-run reconciliation belongs in an action or offline computation, never a Convex query or mutation. The basis check uses one index lookup per claim and does not rescan repeated result occurrences.

Every breach makes reconciliation `incomplete`, with specific, sorted, payload-free reason codes; no row is silently dropped or selected over another. These are narrowing rules within source v3, with no additional version change.

An incomplete reconciliation cannot seal a complete report: source/population coverage remains unknown or the run fails, never silently drops rows. A missing or unknown owner legacy audit makes the cohort legacy audit unknown/null; the cohort audit must also agree across every page. These are run-level obligations for C6.1/C6.2, beyond the existing per-cell-page audit equality refine.

Keys are computation inputs only. Closed report cells, public pages, safe manifests and aggregate exports contain neither key. Direct owner and HTTP ZIP exports continue to withhold entire source snapshots; their existing explicit metadata allowlists are unchanged. Reconciliation diagnostics contain only status/reason codes, and derivation/validation emit no logs. Regressions inject both keys into public/aggregate returns, inspect both actual owner export paths, and assert no computation keys in outputs or logs. No writer, migration, flag or provider operation is added.

#### Owner-explicit integration and publication batches

Session requests keep `resolveArtifactLineageForOwner`, `registerInstructionalArtifactForOwner` and `registerInstructionalArtifactsForOwner`; their owner argument must match `requireAuth`. Identity-less server producers use `resolveArtifactLineageForRecord`, `registerInstructionalArtifactForRecord` and `registerInstructionalArtifactsForRecord`. Their strict owner record is either `{ kind: 'document', id }` or `{ kind: 'audio_job', id }`, with no owner field. Each rereads the record, rejects active or completed account-deletion tombstones and checks current folder/task/room/conversation access as applicable. Every artifact, origin, stable case and source must belong to that record's owner. A forged record object or an owner string cannot grant admission. The record proves only the owner, not that an artifact belongs to it, so C4.3 builds every reference on the server from records it has read. The internal `resolveForRecord` query supports action preflight; capability-authorized handlers call the helpers directly in their own transaction after checking the capability.

The batch envelope is `{ artifacts: [{ reference, validationId }], expectedCatalogRevision }`, bounded to **1–50 distinct artifacts**, the largest single-write publication (a generated Quiz's 50 questions). All decisions must compare the same current catalogue revision and coverage watermark, and the catalogue must have a positive prospective history basis. All members and their complete graphs are checked before any write. One guard advance supplies every receipt's `catalogRevision`, mirroring #364's family-manifest reservation; a stale comparison, duplicate member, reserved case, missing source or exhausted shared read budget rejects the whole batch without partial case changes or receipts. The result is `{ version, lineageIds, catalogRevision, readUsage }`. A transaction registers one batch, because its advance makes a second batch's comparison stale. Larger publications must stop or be explicitly partitioned across transactions and revalidated against a new comparison; they cannot reuse a stale decision across batches. A document never sizes a batch by its chunks: `document_chunk` rows must use `LEARN_ARTIFACT_DOCUMENT_CHUNK_SET_KEY`, one chunk-set row per document revision pinned to the document projection, and any other chunk key is unavailable. The public API contract records each producer's largest publication and the measured 50-member cost.

When batch members share a stable case, its `artifactIdentityValidationId` is set once: an existing proof is kept; otherwise the member that binds the case itself supplies its validation, then the first member in batch order. Single-artifact helpers delegate to the same batch implementation and retain their existing result shape.

Registration moves a stable case's usage class from `unknown` to `instructional`, recording the persisted identity-validation decision. Producers must reuse the stable case for copies, rewrites, restores and equivalent fingerprints. Creating a second case with a duplicate scenario or solution fingerprint makes **both artifacts unavailable**; a new case key never repairs novelty. Existing measurement reservations remain permanent.

#### Projection drift and supersession

`learnV2ArtifactLineage.coverage.test.ts` derives the field list of each of the 31 producer tables from its schema validator, including every union branch. It explicitly classifies 465 top-level/system fields as projected (including joins, selection and ordering) or excluded with a reason. Tracked rows also prove that `artifactContentProjection` reads every projected field and no excluded one, except the named join, index-order and readiness fields consumed by the bounded readers. The differential suite independently compares real consumer payloads and real mutations. `LEARN_ARTIFACT_CONTENT_VERSION` is the single content-projection version, and both payload and manifest digests use one canonical-JSON implementation.

For `document`, `document_chunk`, `session_block`, `flashcard_version`, `learner_artifact`, `measurement_item` and `scoring_spec`, a producer may need a fresh pin while the authoritative revision stays the same. Content-addressed `quiz_question`, `section_block` and `audio_overview` rows may supersede only with an equal payload digest and `sha256:` revision and a changed manifest commitment, after an origin re-pin or a source document's hash or object key changes at the same source revision. Their payload changes still need a new revision. It creates a new sealed row and append-only validation, then calls `supersedeArtifactLineageForOwner` or `supersedeArtifactLineageForRecord` with `{ previousLineageId, replacementLineageId }`. The helper verifies exactly two active rows for the same typed artifact/component/revision, a changed payload or manifest commitment, an admissible current replacement pin, a current complete validation and matching watermark. Classification, authority, derivation and every case/source tuple must be retained. Origin edges retain their original identity and transformation; a successor may explicitly point to the current terminal row of that origin's recorded `nextId` chain, checked within 16 hops and the shared byte budget. An unrelated origin replacement is denied. It only sets the old row's private `nextId`; it never rewrites an old pin, receipt, validation or stable case, and never clears reservation. ### #512 response pins

[#512](https://github.com/wescodess/budds/issues/512) applies [#363 §§1–3](https://github.com/wescodess/budds/issues/363#issuecomment-6651831618) without a writer, migration or flag. Existing `learn-v2.responses.v1` commands, stored legacy assessment responses (`flow = v2_today | v2_canvas` with their historical `baselineEpoch`) and formative/diagnostic branches retain their shapes and meaning. New assessment response storage uses `responseContextVersion = learn-v2.response-context.v1`, `flow = today | canvas`, and a required `measurementContext`: either `{ status: not_enrolled }` with no epoch, or `{ status: admitted, assignmentId, baselineEpoch }`. Only an admitted assignment supplies that epoch; considered/not-admitted assignments never fabricate one.

The frozen pure function `shared/learn-v2-measurement.ts::deriveLearnAssessmentResponseContext` consumes projected, server-read opportunity context and assignment pins. It has no client-authority input or I/O. The parent's clarified rules are:

| Context | Server authority for response flow | Fail-closed cases |
| --- | --- | --- |
| `session` | Session without Canvas attribution is Today; complete Canvas attribution is Canvas. | Malformed session/Canvas pins or a conflicting admitted assignment flow. |
| `planned_measurement` | Admitted measurement assignment's frozen `v2_today` / `v2_canvas` flow, mapped to `today` / `canvas`. | Missing, considered or not-admitted assignment, missing epoch/identity, or unknown flow. New stored planned responses also require admitted measurement context. |
| `calibration` | Explicit `contextPins.origin = today | canvas`, set by the future server creator: V2 calibration route is Today; Adaptive Canvas is Canvas. | Missing/unknown origin or a conflicting admitted assignment flow. Calibration is never defaulted to Today. |

Calibration `origin` is optional only in legacy opportunity/scope shapes so old rows still read; the derivation and new accepted-response storage require it. This clarification is prospective and supplies no calibration writer or backfill. Request schemas reject client `flow`, epoch, measurement context, origin and confidence policy.

`learn-v2.response-delivery-pins.v1` pins `confidenceRequested: boolean` on an opportunity's optional `deliveryPins`; response slots store `confidenceRequested` directly. Future creators/granters must set these from the actual delivered prompt contract, including explicit false. Legacy missing pins resolve to false; the shared slot parser materializes that false. `validateLearnAcceptResponseRequest` compares single-response confidence against the owned slot or validated assessment delivery pins. `validateLearnFinalResponseBundle` independently checks teach-back against its slot's `confidenceRequested` and application against its opportunity's `deliveryPins`, using `resolveLearnResponseConfidenceRequested` for each. `validateLearnMasterySubmission` in the public contract dispatches the strict `{ submission: command }` envelope to the single or bundle validator. Both shapes require integer 1–5 confidence exactly when the relevant server pin requests it, rejecting missing requested confidence and unsolicited confidence without adding a learner interaction. C2.1 must call these helpers with the owned server-read pins before persistence.

Receipts add `result.kind = terminalized` under `commandVersion = learn-v2.response-terminalization.v1`. The result retains the exact `target`, resulting `revision`, `reasonCode = cancelled | abandoned`, and server `terminalizedAt`. The terminalized branch requires the target and forbids `expiresAt`; it follows owning aggregate/account history and the existing command-key index, so C2.1 can replay that same result. A browser close creates no receipt or abandonment fact. Rejections still require their 90-day expiry. The disabled public terminalization success shape reserves `terminalizedAt` alongside its existing target/revision/reason.
