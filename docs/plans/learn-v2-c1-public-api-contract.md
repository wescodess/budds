# Phase C1 public API contract

API version: `learn-v2.public-api.v1`. Implements [C1.3 #423](https://github.com/wescodess/budds/issues/423) for [C1 #413](https://github.com/wescodess/budds/issues/413). Report output is `learn-v2.measurement-report.v3`; source is v4; query and metric definitions remain v1. This contract adds no active response, delivery, scoring, assistance or report writer.

The accepted [baseline](https://github.com/wescodess/budds/issues/359#issuecomment-6651298918), [lifecycle](https://github.com/wescodess/budds/issues/360#issuecomment-6651303610), [responses](https://github.com/wescodess/budds/issues/363#issuecomment-6651831618), [items](https://github.com/wescodess/budds/issues/364#issuecomment-6651739355), [reports](https://github.com/wescodess/budds/issues/366#issuecomment-6652156993), [disclosure](https://github.com/wescodess/budds/issues/373#issuecomment-6651824980) and [scorer identity](https://github.com/wescodess/budds/issues/380#issuecomment-6651838342) resolutions remain binding.

## Registered boundaries

### #573 serial amendment: Today points to Canvas

Post-seal teaching uses the separate [runtime integration amendment](learn-v2-post-seal-teaching-contract.md#integration-amendment-learn-v2post-seal-teachingv1runtime2).
Its three Canvas aliases also serve Today-treatment checks with frozen Canvas
surfaces. Their content and progress states do not widen Today pointers or Canvas
check receipts. Post-seal, help and lesson admission share one bounded window
collector; accepted cancellations can retain only accepted-invalid separate
practice authority under the post-seal gates.

The owner decision of 2026-11-24 retains [Today points](../design/learn-delayed-check/decision.md). `todayCanvasChecks` is a separate default-off capability in the measurement manifest; responses must also be enabled. It selects the check delivery surface for new Today enrollment. Measurement `flow` names the teaching treatment: Today remains `v2_today`; Canvas teaching remains `v2_canvas`. Existing delivery, enrollment, protocol, entitlement, scorer, source and pilot gates remain conjunctive for content and acceptance. This amendment changes no production setting and rewrites no historical assignment or flow.

`learnV2Today.getCheckPointers({ cursor?, pointerVersion? })` has the declared return validator `todayCheckPointersValidator`. When enabled, or for a frozen Today cohort with Canvas checks, `getToday({ pointerVersion? })` also carries the identical `checkPointers` envelope independently of its session `status`, including `empty`. The envelope is `{ status: available | unavailable | disabled | restart_required, reasonCode: string | null, checks: LearnTodayCheckPointer[], isDone: boolean, continueCursor: string | null }`. Disabled results have an empty array, `isDone: true` and a null cursor. The shared semantic contract is `shared/learn-v2-today-check.ts`; pointer fields are closed:

```ts
{
  version: 'learn-v2.today-check-pointer.v2',
  reference: string,
  state: 'ready' | 'saved_scoring' | 'result_unconfirmed' | 'result_ready' | 'closed',
  destination: { kind: 'canvas', threadId: Id<'learningThreads'>, route: string },
  topic?: string,
  timing: 'this_session' | 'about_a_week' | 'about_a_month' | 'earlier' | 'retained'
}
```

Callers opt into the additive version with `pointerVersion: 'learn-v2.today-check-pointer.v2'` on each Today query, including continuation requests. Calls without that argument retain the original strict v1 payload, so older clients continue to parse it unchanged. The lesson's existing embedded `assessment.check` and start/content envelopes retain v1; the version request selects only the `checkPointers` envelope.

The [#579 owner decision](https://github.com/wescodess/budds/issues/579) adds only `topic` and `timing` to the enabled pointer. `topic` is the current objective title, identical to the learner's map title, never a frozen item or question label. It is omitted when the objective, Blueprint, Void or folder is missing, foreign or no longer authoritative, when the Void is archived, or when the title is blank. An owned saved receipt survives that loss without a topic; an unanswered check still follows its existing playability gates. Renaming an objective updates the label on the next read. No fallback title is synthesized.

`timing` is evaluated at read time against the earliest granted teaching receipt for the same owner and assignment, with matching Void, Blueprint and objective. Its `serverTime` records actual teaching delivery. Enrollment, sealed-cold and replacement-creation timestamps do not establish when teaching occurred. The first receipt remains the basis for that assignment's original and replacement checks; a replacement does not reset the teaching age. One indexed first-row lookup, memoized by assignment for the invocation, supplies that time. No receipt timestamp or exact schedule is returned.

For delayed checks, elapsed days means `(Date.now() - serverTime) / 86_400_000`, without calendar rounding. The allowed ready-row and header copy is closed below; the topic title may be shown separately only when present.

| Class | Rule | Ready-row copy | Header copy |
| --- | --- | --- | --- |
| `this_session` | Cold check, regardless of elapsed time | "Check on this topic" | "Start with a quick check on this topic." |
| `about_a_week` | Known teaching age at least 4 days and less than 14 days | "Check on last week's topic" | "Start with a quick check on last week's topic." |
| `about_a_month` | Known teaching age at least 14 days and less than 46 days | "Check on a topic from about a month ago" | "Start with a quick check on a topic from about a month ago." |
| `earlier` | Delayed check younger than 4 days, at least 46 days old, or teaching time unknown/invalid | "Check on an earlier topic" | "Start with a quick check on an earlier topic." |
| `retained` | Retained-purpose check | "Check on an earlier topic" | "Start with a quick check on an earlier topic." |

Unknown teaching time includes a missing receipt, foreign or mismatched scope, or a nonfinite, negative or future timestamp. Its horizon fallback is deliberately generic (`earlier`): a frozen 7/30-day horizon cannot authorize an age claim without a teaching timestamp. A seven-day check still open on day 30 therefore uses `about_a_month` when teaching occurred on day zero. Timing changes with elapsed age even when the opportunity and original clock are unchanged.

`Date.now()` is read when the reactive query evaluates; time passing alone does not invalidate a Convex query. These classes authorize approximate period copy only, with no exact age, due date, countdown or promised transition instant. Their broad buckets intentionally tolerate ordinary snapshot staleness around a boundary without timer-driven invalidation; a later query evaluation recomputes the class. An indefinitely retained snapshot is not a live clock and must not be presented as an exact calendar statement. Neither addition includes an item, case, key, rubric, score or held-out content.

The shared parser and return validator retain the closed v1 shape alongside v2; common reference/state/destination fields are unchanged. With `todayCanvasChecks` off, even previously bound recovery pointers retain their byte-identical v1 shape, with no title reads or added fields. Responses off still dominates. The only schema addition is an exposure index over owner, assignment, purpose, status and server time for the bounded teaching lookup. This extension changes no stored fields, continuation, capability default or C4 golden. The version request is ignored with the capability off, preserving the existing payload even for opted-in callers.

`reference` is the opaque check identity, never an item identity or an authorization. The destination is the owned Canvas route `/app/learn/void/${encodeURIComponent(threadId)}?check=${encodeURIComponent(reference)}`. The `check` query addresses the receipt across refresh and later activity changes. The #442 adapter forwards it as the optional `checkReference` argument to `learnAdaptiveCanvas.getCanvas` or `getCanvasDelivery`. The server checks the owned thread and exact check binding; a reference for another owned or foreign Canvas returns no projection. Before saving, the question must pass the same current Canvas claim, item, source-rights, access, evidence, novelty, revocation and canonical delivery checks as attachment. An unplayable unanswered check has no row, including after a grant or window closure.

After acceptance, question admission cannot remove the receipt. One owner-scoped saved-check reader determines both the Today state and the Canvas receipt. It requires an owned accepted Canvas submission bound to an existing owned thread. Deleted, deleting or foreign threads have no row. Current measurement authority determines whether the check can count; the existing `readSavedLearnScoringState` reader determines whether scoring or the committed result is currently recoverable. The learner's answer is loaded only through `getLearnResponseStateForOwner`. An access denial or unavailable/purged body withholds the answer while retaining receipt metadata. No stored response, frozen pin, result or accounting fact is rewritten.

| Condition | Today state | Canvas receipt |
| --- | --- | --- |
| Unanswered and currently playable | `ready` | Existing Canvas question/grant path. |
| Accepted; scoring has dispatch capacity, an execution is running, or a validated receipt awaits commit | `saved_scoring` | Submitted/scoring receipt with the authorized saved body; no result. |
| Current measurement authority remains valid, but reconciliation is required or a claimed result cannot be verified/read | `result_unconfirmed` | Content-free reconciliation receipt; no result, score or feedback. The authorized saved body may remain available. |
| Current authority and the saved-result reader return an owned committed result | `result_ready` | Feedback receipt carrying that exact existing safe-result DTO and the authorized saved body. Reconciliation takes precedence over a retained attempt. |
| Evidence/source/claim/assignment or acceptance validity is revoked, eligibility is excluded/unknown, the check is terminal, the thread ended/rolled back, adaptive admission was revoked, or unscored work cannot proceed | `closed` | Content-free closed receipt; no question, result, score or feedback. The authorized saved body may remain available. |
| Thread deleted, deleting or no longer owned | No row | No receipt projection. |

Explicit inability to count takes precedence over result availability, both before and after scoring. Thus source purge or lost claim evidence produces `closed`, even when an old attempt remains. Result metadata that cannot be confirmed produces `result_unconfirmed` only while current measurement authority remains intact. Missing or malformed committed-attempt fields never imply a result. Completed recovery retains the stored structural and hard serialized transport bounds independently of current publication admission limits.

Pending/retryable phase metadata alone does not establish recoverability. The shared Today/Canvas saved-check reader checks the existing per-job dispatch limit. Exhausted work with no running execution or validated uncommitted receipt is `closed`, even before another retry updates the stored phase. Validated receipt recovery remains available after lease expiry without another dispatch. Execution lookup uses the scoring reservation's owner/job index and its `maxDispatchAttemptsPerJob + 1` bound; overflow and resource errors propagate. This read-only classification changes no C5 scoring transition or capability-off behavior.

For #442, saved `getCanvas` responses add the closed `checkReceipt` union, shared by `learnCanvasCheckReceiptSchema` and `canvasCheckReceiptValidator`: `{ version: 'learn-v2.canvas-check-receipt.v1', reference, state, submissionId, acceptedAt, confidence?, body }`. `body` is the existing canonical response-body union. Only the `result_ready` branch adds `result`, using the unchanged safe-result contract; other branches reject that field. Numeric score presentation remains outside the approved treatment. Closed/unconfirmed projections contain no assessment phase that could disclose an old pass/fail outcome, no question/stimulus/response specification, no source references and no activity primitive. Their receipt fills the recovery slot; it grants no retry or fresh answer. Saved response text is never copied from a legacy activity field. Recovery can use frozen session identifiers/revisions when dependent records are unavailable; unavailable schedule/timezone fields are null. Receipt metadata requires authenticated ownership, while answer and result content retain their existing access gates. Anonymous and account-deletion denials retain the existing adaptive error shape. With the capability off, C5 still returns `blocked / protocol_not_frozen`. Ownership, active-plan and Blueprint checks retain their authority requirements; inventory overflow and resource errors still propagate.

Today, lesson start and Today content delivery share one lesson gate built on `readTeachingDisclosureChecks`, the set the C4 disclosure guard itself uses: open `preparing`/`ready`/`test_open` checks for the owner that the guard would match against the lesson's teaching scope (Void, folder ancestry and sources), including checks it cannot scope. It applies to the enabled or frozen Today Canvas cohort and to lesson sessions, never to check sessions. The gate classifies each member:

- **Playable** (a current `ready` Canvas pointer): the lesson waits behind it. Today returns `assessment.check` for that check (own objective first, then soonest close), and the start returns the same check without changing the lesson. An unprepared lesson still prepares its own check at start.
- **Unplayable** (an admitted Canvas-bound measurement check without a playable pointer): the start, or the next delivery, closes it in the same transaction through the existing operational-block and cancellation facts, with the binder reason or the stored scheduler reason. This covers missing or mismatched protocol, entitlement or pilot revocation, scheduler blocks, a lost thread and preparing-but-blocked rows. Teaching then proceeds.
- **Other** members the guard would deny (no Canvas owner to close them, or an unscoped submission): Today returns `blocked / open_check_unavailable` rather than a startable lesson.

When the guard is over its eight-open-check bound or cannot resolve the lesson scope, the lesson waits behind any playable open check or returns `blocked` with the guard's reason. Saved answers and expired checks are never closed. A check in another Void is closed only when the guard itself withholds the lesson because of it (a shared source or folder, or a lost thread it cannot scope). Known instruction mismatches (protocol version, window policy, flow or Canvas pins) resolve before instruction recording: the lesson resolves as ordinary teaching, the gate settles its open checks, and nothing throws or rolls back.

The scan reads at most 128 sessions across at most 32 revisions; overflow is `unknown`. An unexpected failure after admission aborts the enclosing mutation, including its facts and source watermark; resource errors propagate. There is no fallback enrollment and no check or invented destination for a non-admitted learner. Direct prospective Today enrollment cannot bypass preparation while the capability is enabled.

### #587 additive Canvas timing and practice reference

With responses and `todayCanvasChecks` enabled, only checks with purpose
`measurement_cold`, `measurement_delayed` or `retained_transfer` carry
`checkTiming` on `assessment` (including the `loadAssessmentCanvas` question
projection) and their saved `checkReceipt`:

```ts
checkTiming: {
  version: 'learn-v2.canvas-check-timing.v1',
  timing: 'this_session' | 'about_a_week' | 'about_a_month' | 'earlier' | 'retained'
}
```

This independently versioned, optional extension leaves the existing assessment
fields and receipt version/state union intact. The shared strict receipt parser
and Convex validator accept the extension. Both Canvas query and delivery reads
use the same helper, earliest granted teaching exposure, scope checks, elapsed-day
buckets and `earlier` fallback as Today pointer v2. Missing topic labels do not
invent a title or remove coarse timing. No exact time or held-out detail is added.
Query-snapshot staleness has the same approximate semantics as Today.

`independent_application` and all other purposes omit `checkTiming`. The approved
delayed-check design does not authorize a timing line for ordinary application
checks. When `checkTiming` is absent, the UI shows no timing line and retains its
existing application content; absence must not be interpreted as `earlier`.
The unknown-class copy fallback below applies only when timing metadata is present.

The owner-approved Canvas entry copy is:

| Class | Canvas copy |
| --- | --- |
| `about_a_week` | A check on last week's work |
| `about_a_month` | A check on work from about a month ago |
| `this_session` | A check on this topic |
| `earlier`, `retained`, unknown | A check on an earlier topic |

Every owned saved receipt also adds this optional, independently versioned
reference, including `result_unconfirmed` and `closed`:

```ts
postSealReference: {
  version: 'learn-v2.post-seal-teaching.v1',
  assessmentOpportunityId: Id<'learnAssessmentOpportunities'>
}
```

It can be passed directly to the existing Canvas aliases `getPostSealTeaching`,
`openPostSealPractice` and `publishPostSealFeedback`, and used as the reference
portion of `authorizePracticeAssistance`. It conveys identity only, with no
content, phase, score or capability claim. An unconfirmed/closed receipt still
omits `assessment` and cannot infer pass/fail or authorize a scoring retry.
The endpoints reauthorize the authenticated owner and the complete post-seal
contract on each read, opening and help replay. An accepted cancellation may
retain separate-case practice, while evidence loss, relevant open checks,
revocation or failed separation deny content. Lessons and hints still require a
valid scored failure; worked examples retain the separate-practice gate.

Neither `checkTiming` nor `postSealReference` is emitted with `todayCanvasChecks`
off, including frozen Canvas recovery receipts, and responses off retains its existing path. No
additional timing reads run in the off state. Today v1 pointers and C4 goldens
are unchanged. These fields introduce no storage, grant, authority or UI change.

Canvas `assessment` (from both question and saved-check reads) and `checkReceipt`
also carry the optional additive field:

```ts
assessmentPurpose?: 'measurement_cold' | 'measurement_delayed' | 'retained_transfer'
```

It copies `opportunity.purpose.kind` only for these three purposes whenever the
responses capability is on, independently of `todayCanvasChecks`. This includes
Canvas-native checks with `todayCanvasChecks` off and frozen-cohort recovery
receipts after rollback, including closed or unconfirmed receipts that omit
`assessment`. `independent_application` and every other purpose omit the field;

Every batch component's complete active lineage, across all keys and representations, must remain non-restrictive and available. A reference reached through a retained origin on a different artifact must still pass retained admission when it is also currently projected. Sibling origins at another key of the same artifact are removed before that partition; their current projected components may receive the same-batch exemption. Writers must still re-register every affected current key in the publishing mutation. Sibling inspection permits a stale root content pin and follows recorded origin-successor chains for inspection only, so either requested key, a multi-key batch or explicit descendant re-pinning can recover. Inspection writes no edges or receipts: each key records new origin pins only through explicit re-pinning or its next publication. Declared-origin checks and re-index classification retain exact origin pins and no component exemption; re-index classification permits only its own document's indexing lifecycle. Propagate every error out of the producer mutation so content, new graph rows and registration roll back together.

#### Descendant re-pinning

`repinArtifactLineageDescendants(ctx, { artifacts })`, `repinArtifactLineageDescendantsForOwner(ctx, userId, { artifacts })` and `repinArtifactLineageDescendantsForRecord(ctx, ownerRecord, { artifacts })` are unregistered, server-only, budgeted helpers. The strict input lists 1–50 preparation-kind identities. Each active teaching row whose origin has a recorded successor, and whose content is unchanged, is superseded by a manifest-only re-pin: its origins point to their recorded active successors, its cases and sources stay, the reservation check runs again and the batch registers under one catalogue advance with the usual non-relaxation guards. Rows whose origins are current, whose content changed or that are not teaching stay as they are. The result `{ version, lineageIds, references, catalogRevision, readUsage }` lists only re-pinned rows. Re-pinning registers output, so it has preparation's enrollment and history requirements.

Whoever registers an origin's successor re-pins the descendants it knows. Otherwise a descendant re-pins before use: its next publication does so through preparation, and an admission mutation calls the helper first. Admission never follows an origin's `nextId` by itself, so a descendant that has not been re-pinned stays unavailable.
