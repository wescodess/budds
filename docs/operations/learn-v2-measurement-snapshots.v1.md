# Measurement snapshot operations v1

C6.2 consumes report source v4 and produces report v3 aggregates using the v1 query and metric definitions. It adds no production principal, approved roster, grant, enrollment, flag, model call or baseline evidence. `LEARN_MEASUREMENT_CAPABILITIES.reports` remains false. The server-only approval catalogue in `learnV2MeasurementReportAccess.ts` is empty. Populating it or activating collection requires the separate owner authorization.

An approval binds the verified full application `tokenIdentifier`, binding/grant versions, cohort, epoch, baseline SHA, frozen protocol and replacement policy to an explicit owner roster. The frozen time must precede enrollment. Viewer grants are server-managed; no public provisioning or self-grant command exists. Public requests contain only an owned grant reference, command key, enrollment interval and cutoff. The service derives scope from the grant and approval and rejects arbitrary learner/stratum filters.

`requestReport` coalesces matching builds and saves command hashes in the private build manifest. Replay is scoped to the approved query/cutoff. A fresh command after completion or a later cutoff creates a new run. `beginReportSnapshot` supplies the same server-only command boundary. `dailyRefresh` uses the current cutoff and schedules its next daily invocation only after an authorized request succeeds; nothing starts that chain automatically. Revocation or disabled capability stops it. While a new run builds, `readReportManifest` may return the last authorized completed run for that interval, with its own run ID, cutoff and extraction dates. Consumers must follow that returned ID; the service never labels the old data with the new cutoff.

`pinReportOwners` persists the sorted roster as source-owner watermark rows in batches of eight. The private control manifest also pins a digest of the complete approval. Source extraction traverses each owner's append-only sequence through that saved watermark, detects gaps, and selects the target epoch's admissions and Independent claims before joining any outcomes. It never reconstructs historical mastery from current projections. Missing captures normalize to unknown; missing or unscored outcomes remain null. Joins verify authoritative attempt/execution references, score and scorer identity pins, current permitted source evidence, and the original first-slot link. Protocol policy governs replacements; the original cold and delayed slots remain primary unless inclusion was predeclared.

Each extraction continuation reads at most four fact records and emits at most eight normalized records. Rows, page digest, byte/population counters, source cursor and next scheduled continuation commit together. Pages are capped at 256 KiB. Runs enforce a 90-day enrollment interval, 10,000 assignments/claims, and 64 MiB of source/normalized input. Ambiguous per-record history, conflicting duplicates, a stuck cursor, a missing page/fact or overflow fails incomplete. No reader silently truncates a population. Replaying a committed page verifies its digest and appends nothing.

`finalizeReport` reads and verifies every saved source-page manifest, reconciles the whole run, fingerprints the canonical normalized inputs and runs the shared computation in an action. C6.3/offline consumers must likewise run reconciliation, fingerprinting and the 10,000-replicate bootstrap in an action or offline at the 10,000-episode / 64-MiB maxima, never in a query or mutation. Output pages are saved idempotently; sealing checks the input digest, source and cell counts, build phase and current revocation. All cells share the computation's run-level legacy audit. Unknown audits remain unknown; fixtures establish no legacy or prospective learning claim.

This is a logical snapshot with a per-owner watermark vector and actual extraction interval, not a global atomic multi-transaction database image. Ordinary post-watermark writes cannot alter its frozen inputs. Later integrity facts, source invalidation or account tombstones immediately withhold cached output. On every direct manifest/page/export/download request, the service rechecks verified principal, active grant, approval scope and current deletion/integrity guards. The additive `by_userId_and_fact_kind_and_sequence` index selects only an owner's integrity facts after the pinned watermark, across all epochs; one match invalidates. It indexes the existing required `fact.kind`, so existing rows are covered without a migration or backfill. Validation reserves five single-record lookups per owner within 3,000 ranges and 8 MiB of document reads, allowing for five maximum-size documents before starting each owner. Only pins and watermarks accumulate bytes: a match in any other guard immediately invalidates. Either exhausted budget returns `source_validation_incomplete` without aggregates. Missing watermarks or changed history coverage also withhold output. A new run rebuilds only permitted evidence.

Online consumers use the audited mutations `readReportManifest`, `readReportCells`, `exportReportPage` and `downloadReportPage` for the frozen safe manifest/status and allowlisted aggregate cells. Each successful acquisition commits a payload-free access record before returning. With reports enabled, the legacy queries `getReport`, `getReportCells` and `exportAggregateReport` return `unavailable` / `audited_access_required`; their capability-off behavior is unchanged. These APIs expose no raw source rows, computation keys, learner identifiers, prompts, answers, private scorer payloads or unrestricted queries. Personal export retains its separate authority and allowlists. Internal source functions have no public raw-data wrapper.

The table-backed fixtures exercise nine owners, several bounded pages, negative gain, missing/unscored endpoints, ordinary blocked claims, post-watermark writes, replays, page faults, overflow, grant attacks and source/account/integrity loss. Their arithmetic is hand-calculated in test comments: 60 to 40 is -20 percentage points; missing both endpoints contributes [-100,100]; cold 60 with missing delayed contributes [-60,40]. These are application accounting checks, not real learning, sample adequacy, scorer/form validation or baseline capture.

## Delayed due-work coverage

The one-minute delayed-check cron is inert unless responses, enrollment, delivery, the V2 rollout flag and a frozen protocol are all enabled. Those gates precede scheduler database reads, writes and scheduling. Source-watermark and assignment writers insert durable `learnMeasurementDueWork` records in their own transaction. Opportunity creation records both open and close times, including an already elapsed `openAt`. A recoverable opening block retains or creates an opening record. Semantic owner/assignment/opportunity keys coalesce outstanding work without a timestamp-window boundary.

Future edges are `scheduled`; due and backed-off work is `pending`. A worker deletes its record only after successful processing commits. Owner initialization processes one assignment per transaction, preserving its pagination, source-sequence pins and fault count across continuations. An incomplete pass restarts the owner scan on a later domain check. Other records process only their assigned episode or opportunity. The shared dispatch lease admits one chain and fences stale continuations; worker generations fence stale jobs. Each step reads at most 16 records from the due-time index, dispatches at most 16 workers and schedules at most one continuation. The chain may perform up to eight consecutive empty follow-ups while jobs finish; the next cron handles remaining work. Empty steady-state ticks schedule nothing. Workers read only their own records and owner-scoped indexes. They never read global queue ranges or the shared cursor.

An access, catalogue, novelty, evidence or protocol block is a domain state. Re-evaluation uses a one-minute-to-one-hour capped interval, shortened to the opportunity's close time. It does not spend the fault budget or abandon a check inside its window. At close, normal processing records the actual blocking reason. Permanent blocks close the same way. A genuine never-playable scheduling miss remains `system_due_work_late`; it cannot overwrite a recorded access/provider block in C6.

The scheduled per-record wrapper invokes its registered processing mutation in a [subtransaction](https://docs.convex.dev/api/interfaces/server.GenericMutationCtx#runmutation). On an exception, the child writes roll back before the wrapper records a fault. Only actual exceptions or failed scheduled jobs spend the eight-fault budget. Exhausted work becomes `parked / retries_exhausted`; it does not alter opportunities or delivery sessions. An opportunity recovery waits until its window closes. Assignment and owner recovery get a later attempt after one hour. Recovery is also per record, with at most three failed attempts before automatic recovery stops in `terminal`. One failed record cannot roll back shared dispatch or prevent other learners' jobs from being scheduled. In-progress and unopened checks remain intact, and a parked assignment never fences later successful materialization.

C6 uses its separate reports gate to check retained work even when scheduling is disabled. Pending, parked and terminal work withholds coverage while its responsibility remains unresolved. A successful normal close records the outcome and retires both opening and closing records, including parked or terminal faults. Successful assignment materialization retires its parked fault; a complete owner scan retires its owner fault. These records do not keep coverage unknown after their work has been successfully reconciled. If processing and all bounded recovery attempts fail, coverage remains unknown until a successful normal close, materialization or owner scan records the missing work. A stored watermark already beyond the cutoff cannot bypass this check. Future scheduled edges are checked by due time. Queue records remain withheld from personal exports and participate in bounded Void/account deletion.

The schema adds optional operational fields, the parked state, a due-time index and an in-flight metadata index. Existing fields, states and indexes remain valid. There is no migration, backfill or capability activation. Local registered tests do not establish deployed cron timing or production contention.

A check never made playable before its window closes records `system_due_work_late`. The pinned opportunity fact retains that reason; reducer code `learn-v2.report-code.c6.2.v8` treats it as `missing_delayed` for both episodes and first-check claims, preserves null outcomes and missing-outcome bounds, and never adds it to learner abandonment or reconciliation. A never-playable claim has no eligibility-time mastery state, so that absence does not make it unknown or novelty-invalid. The reason is reported as `system_due_work_late` beside `missing_delayed`, separate from a learner miss, in aggregate reason codes only. A recorded access/provider block takes precedence over a legacy late label in both episode disposition and first-slot reasons. An on-time playable check without a submission still records `missed_window`. First-slot identity and replacement accounting remain unchanged. Registered cron-only journeys exercise both closures and a sealed five-learner report.
